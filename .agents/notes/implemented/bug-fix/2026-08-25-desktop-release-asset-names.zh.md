# Agent Note: 发布前规范化桌面端 Release 资产名

Status: implemented

[English](2026-08-25-desktop-release-asset-names.md) | 中文

## 问题

桌面端安装器文件名可能包含空格或其他会被 GitHub 在 Release 上传时规范化的字符。发布流程原先会把带目标前缀的原始文件名写入 manifest 与 `SHA256SUMS`，随后却从草稿中下载到名称不同的资产。资产字节保持一致，但不可变发布检查会正确拒绝名称不一致。

## 决策

发布器会在生成 manifest、计算 hash 或上传前派生每个 Release 资产名。候选相对路径的每个片段会保留 ASCII 字母、数字、句点、下划线和连字符，其他连续字符统一替换为一个连字符；目录分隔符转换为双连字符，名称保留目标前缀。签名发布与无签名 Preview 计划都会拒绝规范化后的任何重名。

## 验证

发布 fixture 使用实际带空格的 macOS DMG 文件名，并要求生成计划只包含保守的 ASCII 名称。Preview fixture 还会提供两个规范化后名称相同的不同候选路径，并要求计划构建拒绝该冲突。

## 考虑过的替代方案

**上传后接受 GitHub 改写的资产名。** manifest 与 checksum 文件会描述不存在的名称，消费者也无法把上传前计划作为发布权威依据。

**只比较资产 hash。** 字节相同不能修复失效的 manifest 引用，也不能证明完整预期资产集以预期名称存在。

**复制 GitHub 当前的替换行为。** 依赖未形成约定的标点改写会让本地验证追随远端实现细节。保守的允许字符集合可保持发布器输出稳定。

## 后果

Release manifest、checksum 文件、下载 URL、上传资产与下载验证文件会使用同一组确定性名称。原始候选路径仍是读取并验证源字节的权威依据。未来产物若在规范化后重名，必须在源头更名或配置显式且不同的发布名。
