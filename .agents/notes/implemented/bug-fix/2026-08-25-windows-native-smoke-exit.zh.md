# Agent Note: Windows 原生探针在刷新结果后显式退出

Status: implemented

[English](2026-08-25-windows-native-smoke-exit.md) | 中文

## 问题

最终 maker 验收会在真实安装目录中以 Electron ABI 加载全部原生模块，并实际执行 Sharp、Koffi、ripgrep 与 node-pty。Windows 探针完成所有断言并输出 `outcome: passed` 后，进程仍可能因原生模块保留的 libuv handle 而不退出。父安装器使用同步子进程等待，因此无法继续执行首次卸载、重装与最终卸载。

连续两次原生 Preview run 都在相同边界停止：最后一条日志是完整的原生成功 JSON，此后直到 job 的 60 分钟上限都没有卸载输出。结果内容已经证明原生能力完成，但自然事件循环退出不是该验收要验证的行为。

## 决策

原生探针把成功结果通过 `process.stdout.write` 写出并等待回调，确保 JSON 已交给父进程；随后用成功状态显式退出隔离探针。所有原生能力断言、PTY 退出和结果刷新必须先完成，任何此前发生的错误仍由未处理异常产生非零退出。

安装器驱动在每次首次安装和重装的 `install`、`smoke` 与 `uninstall` 操作前输出平台、阶段和动作。实时日志由此可以判断同步子进程是否返回，以及 Squirrel 生命周期停在哪个动作。

## 验证

Desktop workflow 测试要求原生探针等待结果写出、显式成功退出且不再使用直接 `console.log` 作为终点，并要求安装器驱动保留生命周期阶段日志。原生 Windows Preview lane 仍负责证明成功 JSON 后会继续完成首次卸载、重装 smoke、最终卸载、材料验证和 Preview 验收记录。

## 考虑过的替代方案

**等待所有原生模块自行释放 handle。** 探针不拥有第三方原生模块的全局 handle，且验收只需要证明加载和调用成功；等待没有可观察完成条件，已经导致 job 级超时。

**只给父进程的 native smoke 增加超时。** 超时会把已成功的能力探针标记为失败，并且仍无法进入安装器生命周期。显式结束隔离探针表达了真正完成条件。

**在成功 JSON 前立即调用 `process.exit(0)`。** 标准输出可能尚未刷新，父流程和 CI 会失去权威成功证据。写入回调是退出前置条件。

## 后果

原生探针不会等待与结果无关的 Windows handle，自身也不承担第三方模块进程级清理验证。结果刷新仍是强制前置条件。安装器日志会增加少量阶段行，但能直接区分安装、smoke 与卸载停点；未来新增原生能力必须在显式退出之前完成断言。
